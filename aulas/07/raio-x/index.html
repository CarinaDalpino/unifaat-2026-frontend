Etapa 1

Porta do Nginx sai do hardcode e vira variável de ambiente

O listen 80 estava fixo no config do Nginx. Agora a porta interna vem do .env (NGINX_PORT), e o template finalmente é tratado como template.

docker/nginx/default.conf.template

- listen 80; # Porta em que o NGINX vai escutar
+ listen ${NGINX_PORT}; # Porta em que o NGINX vai escutar, vem do .env
...
docker/nginx/Dockerfile
# Remove o default do container
RUN rm /etc/nginx/conf.d/default.conf
- # Copia o novo config
- COPY ./docker/nginx/default.conf.template /etc/nginx/conf.d/default.conf
+ # Copia o template: na subida, o nginx troca as ${VARIAVEIS} pelo valor do ambiente e gera o /etc/nginx/conf.d/default.conf
+ COPY ./docker/nginx/default.conf.template /etc/nginx/templates/default.conf.template
docker-compose.yml (nginx-container)
env_file:
- .env
ports:
- - "${NGNIX_WEB_PORT}:80"
+ - "${NGNIX_WEB_PORT}:${NGINX_PORT}"
.env.example (e o seu .env)
NGNIX_WEB_PORT=8080
+ NGINX_PORT=80
NODE_WEB_PORT=3000

Por que mudar o destino do COPY

O arquivo já se chamava .template, mas era copiado direto para conf.d/ e nada era substituído. A imagem oficial do Nginx, ao subir, pega tudo que está em /etc/nginx/templates/*.template, troca as ${VARIAVEIS} pelos valores do ambiente (envsubst) e grava o resultado em /etc/nginx/conf.d/.

E o $uri, $host...?

O envsubst da imagem só troca variáveis que existem no ambiente. As variáveis do próprio Nginx ($uri, $host, $remote_addr) continuam intactas. O container já recebia o .env via env_file, então o NGINX_PORT chega sem mais nada.

Atualize seu .env:

quem já tem .env precisa adicionar NGINX_PORT=80. Sem ela, o compose avisa variável vazia e o mapeamento de porta quebra. O NGNIX_WEB_PORT (com o erro de digitação) foi mantido para não quebrar os .env existentes.

Testado:

docker compose config ok; docker compose build nginx-container ok; container com o template em /etc/nginx/templates/ → nginx -t ok e conf.d/default.conf gerado com listen 80; e $uri/$host preservados.

Por que ./src:/app

É o padrão do projeto de Desenvolvimento Web (.:/app). Com tudo na raiz, montar pasta por pasta viraria uma lista enorme. Por cima do src/ montado ficam o nodemodules-volume (em /app/node_modules) e o public-volume (em /app/public), que o compilador do Vite escreve e o Nginx serve.

Por que o nodemon.json

Com o src/ inteiro montado, o nodemon passou a enxergar o public/, onde o Vite escreve .js a cada build. Resultado: 13 reinícios em 10 segundos depois de salvar um .ts. Ignorando public/, resources/, storage/ e logs/, voltou a 0, e uma mudança em routes/ continua reiniciando.

Bônus — dois bugs corrigidos de graça:

ListFilesController e Return404Controller usavam CONSTANTS.DIR/public, que antes apontava para backend/public (pasta que não existia). Com DIR na raiz de src/, apontam para o public/ certo.

Pelo Nginx: /login 200, /docs/ 200 (Swagger com 6 rotas, achou docs/), /arquivo 200 (achou storage/), rota inexistente 404. POST /api/login → 200 + cookie, GET /me/tasks → 200. docker compose run --rm nodecommand-container --help lista migrate/seed.

Novo container: Elasticsearch (só na rede interna)

Mais um servidor TCP/IP em container, porta interna 9200, API REST com JSON. Nada de novo na infra, com uma diferença importante: ele não tem porta exposta.

Sem bloco ports

Nenhuma porta da máquina aponta para o Elasticsearch. Só quem está na app-network chega nele, pelo endereço elasticsearch_host:9200: o servidor web (busca), o command (criar índice, carga inicial) e, depois, o worker (alimenta). O navegador nunca fala direto com o Elastic: toda busca passa pela API.

As três variáveis

discovery.type=single-node: um nó, sem cluster. xpack.security.enabled=false: sem usuário/senha/HTTPS, aceitável só em ambiente local e só porque não há porta exposta. ES_JAVA_OPTS: o Elastic é Java e por padrão quer muita memória.

Como testar em aula:

docker compose exec nodeweb-container curl http://elasticsearch_host:9200. Um curl localhost:9200 na sua máquina não responde, e é isso mesmo que queremos. Na primeira subida ele leva uns 20 a 40 segundos para responder (a JVM inicializando).

Testado:

De dentro da rede: docker run --rm --network fe-2026_app-network curlimages/curl -s http://elasticsearch_host:9200 → JSON com "number" : "9.5.5" e "tagline" : "You Know, for Search". Do host: curl localhost:9200 → sem resposta.

Helper vite(): a View encontra o CSS/JS compilado (manifest.json)

O Vite gera nomes com hash (src/app.aQR1sM3P.js). A View não tem como adivinhar. O manifest.json (ligado desde a Aula 05) tem o mapa fonte → compilado, e o helper transforma isso em tags.

Arquivo novo: utils/vite.js

src/utils/vite.js
+ import fs from 'node:fs';
+ import path from 'node:path';
+ import CONSTANTS from '../bootstrap/config.js';
+
+ /**
+ * Ponte entre a View (servidor) e o Vite (frontend compilado).
+ *
+ * O Vite gera os arquivos com hash no nome (ex.: src/login.COZhj-27.js), então
+ * a View não sabe o nome final. Com build.manifest: true (vite.config.js), o
+ * Vite grava em public/.vite/manifest.json o mapa "arquivo fonte -> compilado".
+ *
+ * Uso na view: <%- vite(["css/app.css", "js/app.ts"]) %>
+ * Devolve as tags <link> e <script> já com os nomes compilados.
+ */
+ export default function vite(entries) {
+ // Lido a cada chamada: o "vite build --watch" reescreve o manifest a cada mudança
+ const manifestPath = path.join(CONSTANTS.DIR, 'public', '.vite', 'manifest.json');
+ const manifest = JSON.parse(fs.readFileSync(manifestPath, 'utf-8'));
+
+ const styles = new Set();
+ const scripts = [];
+
+ for (const entry of entries) {
+ const chunk = manifest[entry];
+
+ if (!chunk) {
+ throw new Error(`Entrada "${entry}" não existe no manifest do Vite (faltou no rollupOptions.input?)`);
+ }
+
+ collectCss(manifest, entry, styles);
+
+ if (chunk.file.endsWith('.css')) {
+ styles.add(chunk.file);
+ continue;
+ }
+
+ scripts.push(chunk.file);
+ }
+
+ const tags = [];
+
+ for (const file of styles) {
+ tags.push(`<link rel="stylesheet" href="/${file}">`);
+ }
+
+ for (const file of scripts) {
+ tags.push(`<script type="module" src="/${file}"></script>`);
+ }
+
+ return tags.join('\n');
+ }
+
+ /**
+ * Um chunk JS pode importar outros chunks que têm CSS próprio:
+ * percorre os imports para não esquecer nenhuma folha de estilo.
+ */
+ function collectCss(manifest, key, styles) {
+ const chunk = manifest[key];
+
+ if (!chunk) {
+ return;
+ }
+
+ for (const file of chunk.css ?? []) {
+ styles.add(file);
+ }
+
+ for (const imported of chunk.imports ?? []) {
+ collectCss(manifest, imported, styles);
+ }
+ }

Antes x agora

Antes: o Nginx entregava o login.html para qualquer um, e o login.ts chamava checkAuthentication() e redirecionava pelo JS, depois da página chegar. Agora: GET /login → ParseCookiesMiddleware → RedirectIfAuthenticatedMiddleware → se o token for válido, 302 para /tasks.html antes de o HTML existir; senão, LoginViewController → render("login"). Com estático isso era impossível: o Nginx não sabe o que é JWT.

Por que apagar o login.html

Com um public/login.html existindo, o try_files $uri.html do Nginx entregaria o estático em /login e a View nunca seria chamada. Saiu do projeto e dos input do Vite; o emptyOutDir tira a cópia antiga do public/.

Quem faz o quê

Servidor: decide se mostra (middleware) e monta o HTML (view). Navegador: interação — o loginListeners.ts não mudou nada, continua achando #login-form, #email-input, #password-input e #login-message pelos mesmos ids.

Bug que já existia (não corrigido nesta etapa):

o botão Sair só limpa o userId da memória e vai para /login. O cookie auth_token (HttpOnly, 10 min) continua válido, então o middleware manda de volta para /tasks.html. O login.ts antigo fazia a mesma coisa no navegador. A correção é uma rota GET /logout no servidor com response.clearCookie("auth_token").

No Chrome: senha errada mostra "Invalid email or password"; senha certa vai para /tasks.html; abrir /login logado volta para /tasks.html; console sem erros.

A conexão com o RabbitMQ

src/database/connections/rabbit.js
+ import { configDotenv } from 'dotenv';
+ import { connect as amqpConnect } from 'amqplib';
+ import { sleep } from '../../utils/sleep.js';
+
+ export default (() => {
+ configDotenv({
+ quiet: true
+ });
+
+ let connection = null;
+ let channel = null;
+
+ const isDocker = process.env.IS_DOCKER === 'true';
+ const rabbitHost = process.env.RABBITMQ_HOST || (isDocker ? 'rabbitmq_host' : 'localhost');
+ const rabbitPort = process.env.RABBITMQ_PORT || '5672';
+ const rabbitUser = process.env.RABBITMQ_USER;
+ const rabbitPassword = process.env.RABBITMQ_PASSWORD;
+
+ const rabbitUrl = process.env.RABBITMQ_URL || null;
+ const rabbitOptions = {
+ protocol: 'amqp',
+ hostname: rabbitHost,
+ port: Number(rabbitPort),
+ username: rabbitUser,
+ password: rabbitPassword
+ };
+
+ const connect = async () => {
+ if (connection) {
+ return connection;
+ }
+
+ const maxAttempts = 10;
+ const retryDelayMs = 4;
+
+ for (let attempt = 1; attempt <= maxAttempts; attempt += 1) {
+ try {
+ const connectTarget = rabbitUrl || rabbitOptions;
+ connection = await amqpConnect(connectTarget);
+ return connection;
+ } catch (error) {
+ if (attempt === maxAttempts) {
+ console.error(`RabbitMQ falhou após ${maxAttempts} tentativas. Host=${rabbitHost}:${rabbitPort} URL=${rabbitUrl ? rabbitUrl : JSON.stringify(rabbitOptions)}`);
+ throw error;
+ }
+
+ console.warn(`RabbitMQ conexão falhou (tentativa ${attempt}/${maxAttempts}), retry em ${retryDelayMs / 1000}s...`);
+ await sleep(retryDelayMs);
+
+ console.log(`Tentando conectar novamente ao RabbitMQ (tentativa ${attempt + 1}/${maxAttempts})...`);
+ }
+ }
+ };
+
+ const createChannel = async () => {
+ if (!channel) {
+ const conn = await connect();
+ channel = await conn.createChannel();
+ }
+ return channel;
+ };
+
+ const assertQueue = async (queue, options = { durable: true }) => {
+ const ch = await createChannel();
+ await ch.assertQueue(queue, options);
+ return ch;
+ };
+
+ const publish = async (queue, message, options = {}) => {
+ const ch = await assertQueue(queue);
+ const buffer = Buffer.from(typeof message === 'string' ? message : JSON.stringify(message));
+ return ch.sendToQueue(queue, buffer, options);
+ };
+
+ const consume = async (queue, onMessage, options = { noAck: false }) => {
+ const ch = await assertQueue(queue);
+ return ch.consume(queue, async (msg) => {
+ if (!msg) {
+ return;
+ }
+
+ await onMessage(msg, ch);
+
+ if (!options.noAck) {
+ ch.ack(msg);
+ }
+ }, options);
+ };
+
+ const close = async () => {
+ if (channel) {
+ await channel.close();
+ channel = null;
+ }
+
+ if (connection) {
+ await connection.close();
+ connection = null;
+ }
+ };
+
+ return {
+ connect,
+ createChannel,
+ assertQueue,
+ publish,
+ consume,
+ close
+ };
+ })();
src/utils/loadJobs.js
+ import fs from 'node:fs/promises'
+ import path from 'node:path'
+ import { pathToFileURL } from 'node:url'
+
+ export default async function loadJobs(jobsPath) {
+ const files = await fs.readdir(jobsPath)
+ const jobs = {}
+
+ for (const file of files) {
+ if (!file.endsWith('.js')) {
+ continue
+ }
+
+ const jobFilePath = path.join(jobsPath, file)
+ const jobModule = await import(pathToFileURL(jobFilePath).href)
+ const fileName = path.basename(file, '.js')
+
+ let jobName = fileName
+ let jobHandler = null
+
+ if (jobModule.default) {
+ if (typeof jobModule.default === 'function') {
+ jobHandler = jobModule.default
+ } else if (typeof jobModule.default === 'object' && typeof jobModule.default.handle === 'function') {
+ jobName = jobModule.default.name || fileName
+ jobHandler = jobModule.default.handle
+ }
+ }
+
+ if (!jobHandler) {
+ const jobDefinition = Object.values(jobModule).find(value => typeof value === 'object' && typeof value.handle === 'function')
+
+ if (jobDefinition) {
+ jobName = jobDefinition.name || fileName
+ jobHandler = jobDefinition.handle
+ }
+ }
+
+ if (!jobHandler) {
+ const functionExport = Object.values(jobModule).find(value => typeof value === 'function')
+ if (functionExport) {
+ jobHandler = functionExport
+ }
+ }
+
+ if (!jobHandler) {
+ continue
+ }
+
+ jobs[jobName] = jobHandler
+ }
+
+ return jobs
+ }

O caminho de um job

O container do worker

Mesmo código (./src:/app), outro entry point: nodemon _worker.js em vez de _web.js. Sem ports, porque não é servidor HTTP. Recebe POSTGRES_*, RABBITMQ_* e ELASTIC_*: é ele que vai alimentar o Elasticsearch. Sem --queue, consome a fila default.
